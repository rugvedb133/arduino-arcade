Tic-Tac-Toe & Checkers, Wired by Hand

Two turn-based games running on one Arduino Mega — no display library shortcuts, no game engine. Every LED, every keypress, and every AI move is driven by code written from scratch.

The Rig

One Board, Two Games

Both games run on the exact same physical setup. I built the checkers board right after finishing tic-tac-toe and reused the wiring rather than starting over. An Arduino Mega reads button presses from a membrane keypad, prints game status to a character LCD, and drives a grid of individually-addressable RGB LEDs that stands in for the board itself.

Arduino Mega 2560
Main controller — runs the game logic and drives every peripheral below.
8×8 WS2812 RGB LED Matrix
The board itself: 64 individually addressable pixels, wired in a serpentine (zig-zag) pattern.
16×2 Character LCD
Status line — whose turn it is, current mode, win and draw messages.
4×4 Switch Membrane Keypad
All player input. No joystick, no touchscreen — every move is a keypress.
Breadboard
Fully breadboarded, no custom PCB — the same rig for both projects.
Jumper wires
Hand-wired point-to-point connections between every peripheral and the Mega.

Module 01

Tic-Tac-Toe

Classic 3-in-a-row, playable two-player or against the CPU. Since the LED matrix is 8×8 and a tic-tac-toe board is 3×3, each cell became a 2×2 block of LEDs, with a full row and column as a yellow grid line between cells — visible in the recreation above.

How it plays

  • Two-player mode — keypad digits 1–9 map directly onto the 3×3 grid. The game blocks moves on an occupied square and checks all eight win lines after every turn.
  • Player vs CPU, easy — the CPU plays randomly for its first couple of moves, which is enough to make it beatable most games.
  • Player vs CPU, hard — a full minimax search runs every turn. It plays optimally and is essentially unbeatable, so I added a short "thinking" pause before its move to make it feel less instantaneous.

In action

Challenges & trade-offs
  • 8×8 doesn't split evenly into 3. While a 9×9 or 12×12 matrix would have allowed real X/O shapes, a 2×2-per-cell layout was the best fit available on hardware I already had — I decided to go with plain color blocks and sacrifice a full row and column in between cells as borders.
  • Memory was tight. The Mega's limited RAM meant the hard-mode minimax search had to stay lean, with no elaborate move caching.
  • Blocking delays break a state machine. Giving the AI a "thinking" pause without freezing everything else meant swapping Arduino's delay() for a manual elapsed-time check in the main loop.

Module 02

Checkers

Full 8×8 checkers, this time using the LED matrix at its native resolution — no compromise layout needed. Pieces move diagonally, capture by jumping an opponent, and promote to "kings" on reaching the far row.

How it plays

  • A real 2D board. Tic-tac-toe's board was small enough to give each square its own named field. Checkers' 64 squares needed a proper 2D array instead.
  • Coordinate-based moves. Rather than cycling through squares, a player types the coordinates of the piece to move, then the destination — both echoed live on the LCD.
  • Kings & highlights. Kings get a distinct LED shade, and the currently selected piece and its legal moves light up in a lighter tone before you confirm.

In action

Challenges & trade-offs
  • The LED strip isn't wired in reading order. It's a single strip snaking back and forth, so each row runs the opposite direction from the last. Mapping 2D board coordinates onto that layout took real trial and error.
  • Minimax didn't survive contact with an 8×8 board. I'd planned a minimax search with alpha-beta pruning for the CPU, same idea as tic-tac-toe's hard mode. But checkers' search tree is far bigger, and the Mega couldn't recurse deep enough in reasonable time. I shipped a simpler move-scanning heuristic instead — a straightforward trade-off between the ideal algorithm and what the hardware could actually do.
  • Joystick input didn't make the cut. I'd originally planned a joystick for cycling through pieces, but flaky analog readings and thin library support compounded with project deadlines pushed me back to the keypad.

Looking Back

What Building Two Games Taught Me

Structuring both games as explicit state machines made a real difference — with no operating system underneath to lean on, having named states and clear transitions kept the game loop predictable instead of turning into a tangle of flags. It's the same reason I split each project's code into separate header files once a single .ino stopped being manageable.

The bigger lesson was the gap between an algorithm on paper and what a microcontroller can actually run in real time. Minimax worked cleanly for tic-tac-toe's small search space; the same approach hit a wall on checkers' much larger board, and knowing when to trade optimality for something that actually runs on the hardware turned out to be as important as the algorithm itself.

And underneath both projects was a lot of low-level peripheral work I'd never had to think about before: scanning a matrix keypad, addressing LEDs individually over a single data line, driving an LCD over a 4-bit parallel interface. None of it is hard in isolation, but getting all of it talking to one Arduino Mega at once, on a shared 500ms tick, is where the real debugging happened.
